# 实施计划与验收门槛

日期：2026-11-15。架构依据：[GPU 帧目标架构](architecture.md)。本文件是后续实施计划，本次仅完成设计、环境核对与工作区准备。

用户约束：Windows + Ubuntu，Intel 核显/NVIDIA 显卡/AMD 核显等主流设备；Ubuntu 优先使用本机 WSL，代码放在 `/home/lqx/code` 下。

## 1. 三次可评审交付

| 交付 | 完成范围 | 完成判定 |
| --- | --- | --- |
| D1：兼容版 | FFmpeg 硬解优先、CPU YUV/RGBA 呈现、软件回退、协议恢复和基础状态界面 | Windows 与本机 WSL Ubuntu 均能独立启动；实际模式可见，1080p60 按实测判定；不依赖 GPU 互通研发成功 |
| D2：首条 GPU 路径 | 同一应用和帧契约下启用至少一个已验证的 GPU bridge，保留 D1 | 证明没有视频像素 CPU 回读，生产/消费同步与停止安全通过；仅将测试过的组合列为支持 |
| D3：发布与设备矩阵 | 固定依赖、跨平台导出、长时间运行、故障注入与能力报告 | 完成本轮 Windows/WSL 矩阵；其他主流设备按后续实机记录逐项加入，不用本机结果代替全部厂商 |

GPU 路径为持续推进的目标，不因 D1 可交付而取消。D1/D2 可以是阶段版本；最终支持范围以 D3 的设备矩阵为准。

## 2. 现状与工作区

已知基础：

- Windows Godot 4.7.2 Mono 与 .NET 8 曾通过最小编译/运行验证，正式接收工程尚未创建。
- `stream_sender` 已实现合规 UDP 发送；默认带 AUD、8 bit YUV420P、关闭 B 帧、约每秒 IDR 并附参数集。提供 `--start-frame`、`--keyint`、`--frames` 等测试入口。
- WSL 发行版 `Ubuntu-24.04`，用户 `lqx`，当前 Ubuntu 24.04.5/WSL2。CMake、G++、Git、FFmpeg 可用，Linux Godot/.NET/vulkaninfo 未在 PATH 发现。
- WSLg 环境与 `/dev/dxg` 存在，NVIDIA 工具可见 RTX 5070 Laptop GPU；当前无 `/dev/dri`。这些是环境信息，不是硬解/图形互通验收。

工作目录固定为：

| 用途 | Windows | WSL Ubuntu |
| --- | --- | --- |
| 接收器 | `D:\Code\udp_streamer_godot\rm_udp_streamer` | `/home/lqx/code/rm_udp_streamer` |
| 发送器 | `D:\Code\udp_streamer_godot\stream_sender` | `/home/lqx/code/stream_sender` |
| 任务脚本/样本/报告 | 外层 `processing/<任务>/` | `/home/lqx/code/processing/<任务>/` |
| 本地工具依赖 | 工作区外层的工具缓存，按任务明确路径 | `/home/lqx/code/.tools/rm-video/`，具体路径由 M0 固定 |

两平台使用独立检出和构建目录。Windows 接收器仓库作为当前变更入口；WSL 从本地 Git origin 获取已提交版本，工作区干净时快进同步。Linux 侧需要改代码时先检查分支/变更并单独提交，再回收变更；不使用覆盖复制或强制重置丢弃未提交工作。原生编译和运行在 Linux 文件系统下进行，不以 `/mnt/d` 作为 Linux 构建目录。

WSL 的两类验证分开记录：协议/原生编译/进程生命周期可以作为 Linux 验证；GPU 和显示报告注明 WSLg 与虚拟化条件。原生 Ubuntu 的 VAAPI、DMA-BUF 或其他 GPU 组合保留独立验收项，本轮不因没有这些机器而阻塞 D1。

## 3. 阶段安排

| 阶段 | 前置 | 工作与产物 | 通过门槛 |
| --- | --- | --- | --- |
| **M0：环境和高风险接口验证** | 本设计 | Linux Godot Mono/.NET 准备；Windows/WSL 原生工具链；锁定 Godot/godot-cpp/FFmpeg；识别实际渲染与解码设备；最小 GDExtension 与 GPU 资源导入/同步探针 | 两平台最小扩展能加载和退出；生成能力报告；每个候选 GPU bridge 明确可行、需后续验证或不支持 |
| **M1：工程骨架与协议核心** | M0 的构建基线 | 创建 Godot/C# 工程和 C++ 模块；UDP、严格重组、有限排序、预算、独立超时清理、诊断 | 两平台重组输出字节一致；异常用例和回绕通过；缓存有硬上限；停止后端口可重新绑定 |
| **M2：解码与 CPU 呈现闭环** | M1 | FFmpeg parser/decoder、FrameLease、硬解和软件模式、CPU YUV 上传及 RGBA 回退、最小画面/状态界面 | `stream_sender` 输入可在 Windows/WSL 的 Godot 显示；颜色/比例/实际新帧率正确；无托管大像素数组路径 |
| **M3：恢复与兼容版交付** | M2 | 缺帧/断流/过载恢复、格式变化、代际控制、启停、路径切换；最小独立导出包 | 正常/异常链路验收；两平台独立启动；发布 D1 及实测报告，未达性能目标的组合明确标识 |
| **M4：首条 GPU bridge** | M0 的可行性结论、M2/M3 帧与生命周期 | 优先在本机可测的同 GPU 组合完成资源导入/复制/转色、生产者与消费者同步、退役；GPU/CPU 路径共用 UI | GPU 模式无像素回读，结果正确；反复启停/缩放/格式切换无提前释放；性能与 D1 可比较；形成 D2 |
| **M5：后端矩阵与回退** | M3、M4 | Windows Intel/NVIDIA 可测设备；WSL NVIDIA 实际路径；自动/强制策略、混合显卡、驱动或格式不匹配、CPU/软件回退 | 每个已测组合有实际后端与结果；强制模式错误明确；不存在静默回退或逐帧重复探测；未测 AMD/原生 Linux 项目保持待验证 |
| **M6：发布和稳定性** | M5 | 两平台固定依赖与导出、30 分钟运行、故障注入、版本和能力清单、使用/排错文档 | D3 通过本轮矩阵；无持续内存/队列增长，无残留线程/端口；发布包在干净环境可启动 |

M0 对 GPU 互通只做受控可行性验证，不把所有后端实现提前塞进准备阶段。若某条互通路径需要未开放的引擎同步或内存能力，记录事实并转交替代方案；M1–M3 继续推进。M4 仅在有安全资源契约的候选上实现。

在 M0 明确图形接口与工具链后再细化工期。GPU bridge 的主要不确定性是引擎/驱动互通条件，不应在验证前用固定人日掩盖这项风险。

## 4. M0 必须产出的决策记录

1. **依赖清单**：Godot 与导出模板、godot-cpp commit、FFmpeg 版本/构建选项/动态库 ABI、C++ 编译器/标准库版本、架构和文件校验值。
2. **Linux 准备**：在 `/home/lqx/code` 内准备对应 Linux Godot Mono、.NET SDK 和构建依赖；缺少 Ninja 可使用其他已验证 CMake generator，不把 PATH 中未发现当作系统一定未安装。
3. **设备身份**：Windows 渲染 GPU 与 D3D11/CUDA 设备；WSL Godot 实际渲染设备与 CUDA 设备；记录是否同一物理适配器或虚拟化映射。
4. **硬解证据**：真实 HEVC 样本解码输出硬件帧，记录 profile、位深、格式和后端。`ffmpeg -hwaccels`、`nvidia-smi` 只作探测，不能作为完成标准。
5. **GPU 图像证据**：目标外部内存格式可导入且画面正确；明确扩展、资源创建标志、格式/布局、同步机制与释放条件。
6. **退出证据**：一帧提交后立即停止/重建也不会提前释放。仅在渲染线程执行或等待若干帧不算 GPU 完成证据。

每条 GPU bridge 的输出记录为 `feasible`、`unverified` 或 `unsupported`，附具体原因与可用 CPU 回退。Godot 渲染器切换需重新启动并单独测量，不能在会话中无声切换。

## 5. 验证矩阵

### 5.1 当前可执行与后续扩展

| 环境 | 本轮验证内容 | 当前证据/限制 |
| --- | --- | --- |
| Windows + NVIDIA 独显 | D3D11VA/CUDA 实际解码、CPU 呈现、首条 GPU bridge 候选 | 本机有 RTX 5070 Laptop GPU，接收器未实现 |
| Windows + Intel 核显 | D3D11VA、CPU 呈现、显卡选择与混合显卡回退 | 本机有 Intel Arc 140T，须实际选中并验证 |
| 本机 WSL Ubuntu + NVIDIA | 原生构建、协议、CUDA/NVDEC 解码、Godot CPU 呈现；GPU bridge 按实际能力验证 | WSL 能看到显卡；Godot/.NET 和渲染能力待 M0 完成 |
| Windows + AMD 核显/显卡 | D3D11VA 及呈现/回退 | 设计覆盖，需要对应设备验证后才能声明支持 |
| 原生 Ubuntu + Intel/AMD | VAAPI、CPU 呈现、DMA-BUF/Vulkan 互通 | 当前 WSL 无 `/dev/dri`，留待具备设备环境时验收 |
| 原生 Ubuntu + NVIDIA | CUDA/NVDEC、CPU 与 GPU 呈现 | 与 WSL 分开记录，不以 WSL 结果直接代替 |
| 任意环境软件模式 | 软件解码正确性与可达到的速率 | 必须可显式选择并显示状态，不假定任意 CPU 都满帧 |

首批常规渲染用 Mobile/Vulkan；Compatibility/OpenGL 验证 CPU 路径。增加 Forward+ 或 D3D12 时记录为新的渲染组合。GPU 互通功能开关与实际探测共同控制，未经验证的厂商组合不能被一次自动探测误标为已全面支持。

### 5.2 协议与异常

任务目录中的独立发送/代理工具注入：正常、帧内/跨帧乱序、重复、缺片、迟到、短/超长包、短中间片、越界序号、同帧长度冲突、同序号内容冲突、超大声明、未知来源混入、无新包时的清理、65535→0、发送器重启和起始任意帧号。

现有发送器用于生成有效输入与可控关键帧间隔，不为验证方便改动正式协议。故障注入代理、抓包回放和基准脚本放入 `processing`。从不同平台发出相同样本，应得到相同重组码流；跨 Windows/WSL 网络使用实际可达地址并单独核对绑定和路由，不把 localhost 行为当作所有 WSL 网络配置的保证。

### 5.3 媒体与帧接口

- 同样的码流比较软件与硬件输出；使用色条/灰阶/运动和裁剪标记验证颜色、范围、UV 顺序、stride、尺寸与可见区域。
- 默认样本为 8 bit、无 B 帧；另外准备不依赖 AUD、含 B 帧、尺寸变化和 Main10 SDR 的样本，覆盖 parser/格式能力判断。未支持的格式应明确拒绝或按配置转换，不能输出错误图像。
- 参数集缺失/更新、从非关键帧中途接入、关键帧丢失、恢复中的重复/迟到包均需覆盖；恢复耗时分成等待上游随机访问点和本地处理两部分。
- 检查旧 stream/resource generation 的帧绝不进入新画面；帧丢弃、路径切换和关闭都归还引用。
- SDR 为首版显示范围；HDR 输入检查明确的未支持/转换策略，避免悄悄误解释。

### 5.4 GPU 与生命周期

- 后端必须分别证明生产者写入完成和消费者读取完成。
- 首先用小图和可识别内容验证格式/共享，再用真实 HEVC 图像；分别测试停止、窗口变化、格式改变和设备/后端错误。
- 注入失败时，GPU 必选模式应报错，自动模式应切 CPU，并展示原因；不把 GPU 解码仍开启时的回读路径标成纯 GPU 呈现。
- 校验 CPU 回读计数/字节、实际调用路径及必要的图形诊断；仅凭低 CPU 占用不能证明无回读。
- GPU 在途槽不足时可丢未提交显示帧，不能覆盖在用纹理或强制归还 AVFrame；CPU 上传也需验证输入生命周期。
- 在途任务无法安全退出时不继续创建新会话；不使用 `RenderingDevice.sync()` 假装完成全局 Godot 渲染同步。

## 6. 性能与交付验收

| 项目 | 初始目标/口径 |
| --- | --- |
| 输入 | 有效 1920×1080、60 fps；固定样本、码率/profile/位深，记录发送器是否真的达到 60 fps |
| 吞吐 | 接收、完整重组、解码、新画面提交分别统计；持续接近输入速率，队列年龄不增长；不得用窗口 FPS 冒充视频 FPS |
| 客户端处理延迟 | 对能证明输入输出关联的样本，建议首包到纹理提交 P95 ≤ 50 ms，记录 P99；M0/M2 根据实测冻结条件，不作为已达成结果 |
| 显示延迟 | 纹理提交不等于实际显示；摄像头到屏幕使用独立拍摄/计时方法测量，记录 VSync、显示刷新率与 WSLg 条件 |
| 帧率观察 | 选定稳定窗口统计平均/低分位速率、跳过显示帧和掉帧原因；正常无注入样本不应持续缺失图像或积压 |
| 长时间运行 | 至少 30 分钟，覆盖自然回绕；预热后内存和 GPU 资源无持续增长，预算始终有效 |
| 故障 | 随机/突发丢包、断流、重启、过载、端口占用、后端失败均可观测；恢复依赖上游关键帧时如实记录 |
| 启停 | 至少 50 次开始/停止/重连，检查线程、Socket、FFmpeg 引用、纹理与在途资源；这是有意义的生命周期检查，不是仅测 UI 按钮 |
| 发布 | Windows 与 WSL Linux 包可用明确依赖启动；动态库版本固定、许可证声明齐全；无调试样本/脚本混入正式包 |

每份性能报告包含提交号、依赖版本、OS/WSL、GPU/驱动、渲染与解码设备、实际路径、样本参数和场景。兼容路径和 GPU 路径在同一条件下比较，不能只用解码耗时代表总耗时。

## 7. 风险与决策规则

| 风险 | 处理与决策点 |
| --- | --- |
| Godot 全局设备无法安全接入外部同步 | M0/M4 验证；失败则该组合用 CPU 呈现，记录是否值得单独研究引擎扩展 |
| WSL 渲染设备与 CUDA 设备无法直接互通 | 本轮先验收 CPU 路径；GPU 路径单列结果，不推断原生 Linux 也不支持 |
| 真实设备格式不同于模拟发送器 | M1/M2 保留 parser/格式抽象，实机确认固定分片和访问单元边界；不把模拟器参数当官方保证 |
| 核显/独显混用 | M0/M5 明确设备身份并选择同设备候选；其他情况走经过验证的中转 |
| 硬解可用但总耗时更差 | 比较回读/转色/上传和等待，按证据选择路径；不因“硬解”标签忽略结果 |
| 原生库或驱动崩溃影响 UI | 单进程首版不保证隔离；若后续加入控制业务并要求故障隔离，单独设计 Worker 和资源传输协议 |
| 未具备 AMD/原生 Ubuntu 测试设备 | 架构和接口覆盖，矩阵保持待验证；获得设备后执行相同验收，不提前宣称所有型号均通过 |

## 8. 任务管理

每个阶段拆成可独立评审的提交：环境/构建、协议、帧契约、解码、CPU 呈现、恢复、首条 GPU bridge、后端扩展、发布。每项工作在外层 `processing` 建立任务目录，包含执行计划和只追加的处理记录。

临时测试工程、样本、故障注入与性能脚本放在 Windows/WSL 对应的 `processing` 目录。测试任务报告要能关联生产提交；平台间使用 Git 传递源码，构建产物保持独立。

下一项具体任务是 **M0：两平台依赖与最小原生扩展验证**。它的输出必须足以确定 FFmpeg 固定版本、Godot/C++ 工具链和首条 GPU bridge 的可行路线，再进入正式视频功能实现。
