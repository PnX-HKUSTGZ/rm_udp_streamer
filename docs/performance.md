# 呈现节奏与 CPU 准备

1080p60 的解码吞吐、向引擎提交的新画面数量、显示器实际扫描是不同指标。诊断使用真实新纹理提交的完整一秒窗口，不把主循环的处理频率当作视频帧率。

界面的“画面节奏”或启动参数 `--cadence auto|display|responsive|engine` 控制处理与显示同步：

| 模式 | 行为 |
| --- | --- |
| 自动 | Windows 硬件渲染采用低延迟；Linux、软件渲染及启动时已有非零帧率上限或非默认 VSync 时沿用启动设置 |
| 显示同步 | 启用 VSync，主循环由显示节奏约束 |
| 低延迟 | 处理上限 120 次/秒；Vulkan 使用 Mailbox 同步，Compatibility/OpenGL 关闭 VSync |
| 沿用引擎 | 恢复进程启动时的帧率上限及 VSync 设置 |

低延迟模式使 60 fps 输入更快被呈现端消费，代价是更高的 CPU/GPU 负担和功耗。OpenGL 关闭 VSync 后可能出现撕裂；可切回“显示同步”。Mailbox 的可用性取决于渲染器与显示驱动。会话完全停止后恢复启动设置。显式选择“低延迟”会覆盖引擎设置。“自动”读取启动时的实际限制；若要明确保留“不限帧且默认 VSync”这种与默认值相同的设置，请选择 `--cadence engine`。

Windows 低延迟模式为当前进程申请 1 ms 定时精度，并请求系统在窗口被遮挡时仍尊重该精度。这样可避免 Windows 11 的后台定时器降精度使 120 次/秒上限变成短间隔与约 16 ms 间隔交替。该请求也会增加后台功耗；切换模式或停止时配对释放定时器请求，恢复所修改的进程策略位。系统不支持或拒绝请求时，界面提示且诊断记录原因，接收仍可运行。最小化时没有实际画面扫描，提交率不能用作显示验收。

CPU 路径保留顺序解码，并把回读、平面整理及 RGBA 转换交给独立准备线程。待准备原始帧和在途准备各最多一张；准备结果未被取走时暂停准备。消费者变慢时，在回读之前替换原始帧，避免转色长期阻塞压缩流消费。GPU 路径继续直接交付硬件帧引用。

准备器最多持有三份可复用 CPU 输出存储，只复用没有外部消费者的存储。硬件回读和编码空间 RGBA 临时存储按布局复用，裁剪与色度位置变化仍重新应用相应转换。保留 CPU 平面到 Godot 的复制和 GPU 私有纹理到显示纹理的复制；这些复制服务于明确的资源所有权与同步。分配和复制计数的范围见 [诊断说明](diagnostics.md)。

上传端按平面复用 Godot 字节存储，通过写时复制保护仍在使用的旧图像。图像对象仍逐次创建，像素仍从准备缓冲复制到上传存储；缓存不是零复制路径。

切流、格式变化、后端回退和停止会使旧准备结果失效；准备线程没有解码器状态的写入权限。准备错误由解码线程在安全边界处理。设备初始化时间与等待下一个可恢复关键帧的时间需分别观察。

以上为实现策略，不构成设备性能认证。2026-11-17 用户将当前接受目标调整为：180 秒预热后，1800 秒完整窗口的平均新提交至少 55 fps。四条已测当前候选本地回放路径达到该目标；Windows 短时卡顿记录保留，不承诺每秒至少 55 fps。关联本地首片到提交 P95≤50 ms/P99≤100 ms、资源和正常退出检查继续保留；详见[当前接受范围](evidence/r6/acceptance-55fps.md)。

原正式 1080p60 等级仍表示平均新提交至少 59.4 fps、一秒窗口 P10 至少 58，并满足上述延迟条件。它与用户新接受的平均 55 fps 目标分开，历史结果不重写。局域网、真实图传、WSL 软件渲染、RGBA 转换以及未实测的设备组合均单独列出能力范围。
