# Windows 发送停顿与独立输入诊断

2026-11-17。对应运行候选 `1366817`，不替代[正式长测失败](candidate-1366817-performance.md)。本轮没有修改产品、HEVC 样本、分片格式、接收预算或性能门槛。[机器可读记录](windows-pacing-diagnostics.json)将结果与包、原生库及原始记录摘要关联。

## 发送调用定位

首先以原发送器做 10 秒预热、180 秒输入，并在独立进程以 1 Hz 记录 CPU 活动：得到 54.7833 fps/P10=38，23 次组超时、30 次恢复。慢发送所在区间的系统 CPU 活动较高，发送进程自身 CPU 也增加，但这些相关性不能归责某个后台程序。

随后单独记录每帧线程 CPU 和垃圾回收。该轮没有超过 50 ms 的整帧发送，最慢 48.9922 ms，对应量化后的线程 CPU 为 46.875 ms，且没有与垃圾回收重叠；最长垃圾回收约 4.4 ms。这轮不能认定或排除此前失败由垃圾回收引起，也不作为重新获得正式通过的证据。

逐网络调用诊断复现两次约 60 ms 的长发送，约 99% 的整帧时间位于 `sendto` 调用内。进一步预先声明的一组顺序对照将可写等待与实际发送拆开：

| 诊断方式 | 平均 / P10 fps | 最长整帧发送 | 其中等待可写 | 其中实际发送 |
| --- | ---: | ---: | ---: | ---: |
| 显式 select + 非阻塞 UDP | 59.3444 / 58 | 78.3292 ms | 0.9673 ms | 76.7008 ms |
| 阻塞 UDP + Windows 原生 1000 ms 超时 | 59.3778 / 59 | 85.6329 ms | 无 select | 85.1951 ms |

两轮各有一次有效测量区的组超时，正常退出。主要时间仍在实际发送调用，线程 CPU 以内核计数为主；去掉 select 没有解决问题，因此没有把它作为修复采用。CPU 计数有约 15.625 ms 量化，不能逐微秒解释。尚无足够内核堆栈证据识别具体驱动或过滤器。

以上不同诊断的观测开销、系统负载及 socket 实现有差异，不构成严格性能改善估计；所有完整记录均保留，没有按表现选择轮次。

## 独立输入与入站规则

为了进一步检查接收端，使用现有 AMD Ubuntu 主机通过局域网发送同一已校验样本。小包探测在本机 UDP 3334 完整收到 128/1400 字节各三包；随后发行程序的 10/60 秒诊断虽然正常监听和退出，却没有收到任何数据报，因此没有解码或提交窗口。远端 4440 帧没有超过一帧发送迟到，整帧发送 P99 为 0.402046 ms；两台机器的单调时钟没有被混用于 CPU 统计。

有效 Windows 防火墙规则中，当前发行程序路径存在启用的 TCP/UDP 入站阻止，覆盖专用和公共网络；旧发行包与探测程序对应的是允许规则。独立输入诊断的零收包不能记为解码失败，也不能算性能验收。

已备份原规则，并准备可恢复的修改：只为当前候选在专用网络开放测试机来源的 UDP 3334，将其现有 UDP 阻止保留在公共网络，TCP 规则不变。该操作需要管理员权限，已请求用户确认，记录时尚未执行；没有关闭防火墙或移动程序来绕开阻止规则。

原始脚本、全部失败、控制消息和采集结果在外层 `processing/2026-11-17-rm-windows-pacing`。诊断包装副本曾有一次辅助文件相对路径错误，发生在接收程序启动前，修正后的运行另存，旧记录保留。当前没有新的 CUDA 正式性能通过结论，R4/R6 仍未完成。
