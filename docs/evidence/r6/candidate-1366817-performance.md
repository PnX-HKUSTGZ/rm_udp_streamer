## Windows 失败与尚未完成的项目

首次 10/60 秒预检为 57.2667 fps/P10=55，失败原件保留。传输独立诊断后，事前声明的一次 v2 复核短测通过（59.8833 fps/P10=59），但正式 180/1800 长测失败：1800 个完整秒窗中有 183 个低于 58 fps，其中 13 个没有新提交。没有再执行第三次同条件正式重跑。

正式测量段有 274 次整帧分片发送超过原有 50 ms 组装期限，最慢 132.8293 ms；发送开始迟到超过一帧共 1813 次。原生测量区有 201 次超时缺组、45 次压缩队列过期、136 个队列丢弃和 258 次恢复。全部输入期间共发送/接收 2752800 个 UDP 数据报，总数相等；这不表示每组均在期限内完整到达。GPU 上传 CPU P99 仍小于 1 ms，不据此把所有掉帧归因于 GPU 性能或产品回归。

外部观察器采样 P95 约 35.86 ms；274 次长发送中只有 33 次与其执行区间重叠，不能认定观察器是唯一原因。没有采集到足够的系统调度因果证据来归责某个后台进程。全程观察到接电、未开启节电、窗口可绘制，但发送进程为 NORMAL（32），引擎为 ABOVE_NORMAL（32768）；未获得本轮审核预先要求的普通引擎优先级结果。此前历史阶段只要求发送器普通优先级，不据此追溯否定历史数据。

该次调度在 CUDA 正式失败后结束，CUDA 诊断四轮和原定 D3D11VA 后续步骤均未执行，不能借用旧包结果填补。后续先完成下述短诊断和优先级来源核验，再单独声明并运行 D3D11VA 序列；没有放宽接收预算或改动帧率门槛。

后续[逐调用与独立输入诊断](windows-pacing-diagnostics.md)已将长发送收窄到实际 UDP 发送调用的内核执行阶段，显式 select 对照没有解决问题；独立局域网输入另发现当前发行路径的有效入站阻止规则。这些诊断不将本次正式失败改写为通过。

### Intel D3D11VA 首次独立序列

在查看本轮结果前，声明同包 D3D11VA/YUV/Mobile 序列：10/60 预检、180/1800 正式测量，随后才是完整 off/on/on/off。沿用冻结的发送器、样本、统计方式和门槛，不带逐包探针。发送器 NORMAL（32）、Godot 原有默认 ABOVE_NORMAL（32768）明确作为本轮观察条件，没有手动提升优先级。旧 CUDA 失败没有重跑。

预检平均 59.916667 fps/P10=60，P95/P99=37/41 ms，通过。正式测量得到上表结果，1800 个完整秒窗中 129 个低于 58 fps、10 个零提交；平均帧率失败后停止序列，四轮诊断对照未启动。正式期间实际解码设备始终为 Intel Arc 140T（LUID=0:92536），渲染设备为 RTX 5070 Laptop；全程观察到接电、未启用节电、窗口可绘制及 165 Hz 显示，优先级符合事前条件。

正式发送窗口的 108000 帧中有 274 次整帧发送超过 50 ms，最长 111.2546 ms；超过一帧的发送迟到为 1463 次。完整输入期间 2752800 个数据报的收发总数一致，204 个组超时；原生测量区另有 34 次压缩队列过期、88 个队列丢弃、236 次恢复及 726 次解码后最新帧替换。总收包数一致不能证明每组及时到齐，也不能消除恢复期间未产生新画面的损失。

六个 300 秒窗口平均帧率依次为 59.9333、59.66、48.1033、55.9233、59.8833、59.75；全部窗口纳入最终结果，没有排除中段低帧率。274 次长发送中 35 次与资源观察器重叠，仍不足以归责某个系统进程、驱动或过滤器；本轮未加入内核堆栈观测，也不能把此前 CUDA 的逐调用证据当成本轮直接观测。

每个资源分窗有 300 个进程样本，RSS 中位数约 934.20→940.08 MB，最后三个窗口约 939.96→940.08 MB，线程 61–62、句柄 1032–1036；有限时长记录不证明不存在泄漏。预检与正式结果均用原算法从完整记录复算一致，正常退出、视频资源归零、端口重绑和进程显示策略恢复通过。此项只新增失败的性能证据，没有改动运行库。

原生 Ubuntu NVIDIA、Windows AMD 仍缺设备；当前包实时图传验收也未完成。R4/R6 保持未完成，没有提前提交阶段完成审查。
